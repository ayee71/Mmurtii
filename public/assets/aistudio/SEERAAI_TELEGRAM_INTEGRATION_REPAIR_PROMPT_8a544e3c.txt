3. TELEGRAM WEBHOOK: CORRECT AUTHENTICATION AND RELIABLE PROCESSING
Implement or repair POST /api/telegram/webhook using Telegram Bot API webhook semantics.

A. Webhook secret validation
- Configure Telegram setWebhook with a strong, randomly generated secret_token stored only in the server-side secret manager/environment.
- Validate the incoming HTTP header X-Telegram-Bot-Api-Secret-Token against the configured secret_token.
- Use a constant-time comparison where supported.
- Reject missing or incorrect secret headers when webhook-secret validation is enabled. Fail closed if production configuration requires a secret but it is absent.
- Never log, return, expose, or put the bot token or webhook secret into frontend code, source maps, health responses, error messages, or ordinary logs.
- Do NOT describe Telegram's webhook secret-token header as an HMAC signature. Telegram's Bot API webhook authentication mechanism is the secret_token request header. HMAC-SHA-256 validation belongs to Telegram Mini App initData validation (see Section 4). If the application also has a separately designed HMAC mechanism, document its exact message format and key management; do not confuse it with Telegram's native webhook header.

B. Update validation and idempotency
- Validate the JSON body and supported Telegram Update shapes before processing.
- Handle at least message, edited_message, channel_post, and edited_channel_post updates when they are part of the currently configured allowed_updates list and the existing product behavior requires them.
- Use update_id as the unique idempotency key for webhook updates. Persist processing state or an equivalent durable deduplication record using the existing storage architecture.
- A duplicate update must not create duplicate archive records or send duplicate bot replies.
- Handle out-of-order delivery safely; do not rely on update_id being perfectly sequential.
- For channel posts, use the Telegram chat identifier and message_id as a stable archive identity. Preserve edited post revisions or update the existing record according to the current archive model; do not silently lose edit history if the system currently tracks it.
- Reject malformed or unsupported payloads safely without crashing the server.

C. Serverless execution and timeout control
- The webhook handler must complete its synchronous work within the actual hosting platform's request budget.
- Do not acknowledge an update with HTTP 200 before it has been durably accepted for processing. If a durable queue or job store is available, persist/enqueue first, then acknowledge.
- Do not rely on an unawaited background Promise after sending the response. Serverless runtimes may freeze or terminate the invocation.
- If no durable queue exists, use the safest pattern supported by the existing platform and storage. Do not add a new paid service or infrastructure resource without documenting it and obtaining owner approval.
- Keep expensive legal classification, document extraction, AI analysis, and long-running Telegram API calls out of the initial webhook acknowledgment path. Execute them through the existing durable job/queue mechanism where available.
- If durable acceptance fails, return a retryable non-2xx response so Telegram can retry. Combine this with idempotency to prevent duplicate side effects.
- Set explicit timeouts for outbound Telegram Bot API calls and other external services. Respect Telegram 429 retry_after responses, retry transient network/5xx errors with bounded exponential backoff and jitter, and do not retry permanent 4xx errors blindly.

D. Webhook lifecycle

- Preserve webhook mode. Do not switch to getUpdates/long polling, call deleteWebhook, or set drop_pending_updates=true as part of a repair.
- Do not call setWebhook on every application startup or on every health check. Webhook registration/rotation is a controlled provisioning action, not ordinary request handling.
- Ensure Telegram's required HTTPS/TLS endpoint behavior is met by the existing hosting configuration.

4. TELEGRAM MINI APP INITDATA: SERVER-SIDE HMAC VALIDATION
The Telegram Mini App authentication process is distinct from webhook request authentication.

A. The Mini App must send the raw Telegram.WebApp.initData string to the backend. Do not authenticate using initDataUnsafe or user IDs supplied independently by the browser.
B. Validate initData on the server using Telegram's documented HMAC-SHA-256 procedure and the bot token (or an approved securely stored derived secret if the existing implementation uses one correctly):
   - Parse the raw query-string fields without changing their original values.
   - Exclude hash from the data-check-string and retain it for comparison.
   - Sort the remaining key/value pairs alphabetically and join as key=value lines using newline characters.
   - Derive the secret key using HMAC-SHA-256 with the literal key "WebAppData" and the Telegram bot token as the message, following Telegram's documented algorithm.
   - Compute HMAC-SHA-256 over the data-check-string with that derived key.
   - Compare the computed hexadecimal digest with the supplied hash using a constant-time comparison.
C. Validate auth_date and reject expired/stale initData according to a documented short validity policy and reasonable clock-skew allowance. Do not accept arbitrarily old initData.
D. Validate required user fields and parse them only after signature validation. Never trust browser-provided user_id, username, role, institutionId, or permissions without deriving/confirming them through the authenticated server-side identity and existing authorization model.
E. Enforce the existing SEERAAI PRO role-based and institution-based access controls after Telegram identity validation. Telegram identity alone must not grant judge, registrar, administrator, auditor, or other privileged application roles.
F. Never expose BOT_TOKEN or any derived secret to the client. Do not log raw initData, hash values, or full personal profile payloads.
G. If the current Mini App uses a different approved validation library, inspect its compatibility and tests before changing it. Avoid introducing a dependency unless needed and compatible with the current runtime.
