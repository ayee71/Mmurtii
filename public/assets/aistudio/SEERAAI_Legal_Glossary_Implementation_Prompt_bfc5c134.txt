SEERAAI PRO — LEGAL GLOSSARY MODULE
IMPLEMENTATION PROMPT FOR GOOGLE AI STUDIO

PURPOSE
Implement a complete, searchable, trilingual Legal Glossary inside the EXISTING SEERAAI PRO application. The glossary must preserve established Ethiopian legal terminology and provide accurate, concept-aligned entries in Afaan Oromoo, Amharic, and English. Authenticated authorized users must be able to submit new terms and proposed corrections. New or changed legal terminology must pass review before becoming part of the approved glossary.

CORE USER FEATURES
A. Search and browse
- Provide a prominent search field that searches Afaan Oromoo, Amharic, and English at the same time.
- Search preferred terms, approved synonyms/alternative spellings, and definitions. Return the same legal concept regardless of which of the three languages was used for the search.
- Support exact phrase and ordinary word searches, case-insensitive matching, Unicode-safe text handling, punctuation/whitespace normalization, and pagination or incremental loading.
- Use Unicode NFC normalization. Do not strip Ethiopic characters/marks or apply lossy transliteration. Do not use crude fixed-length stemming that can merge different legal concepts. Add language-specific normalization only where it is safe and tested.
- Rank exact preferred-term matches above synonym matches, and synonym matches above definition-only matches. Show why a result matched where practical.
- Include filters for legal domain, jurisdiction, and approved status. Ordinary users should see approved/published entries only. Reviewers may have a separate pending-review view.
- Add clear empty, loading, error, and no-results states. Search must not expose pending submissions to unauthorized users.

B. Glossary entry detail
Each approved entry must include:
- Stable term ID and canonical concept ID.
- Preferred term in Afaan Oromoo, Amharic, and English.
- Approved synonyms or alternative spellings for each language, clearly distinguished from the preferred term.
- A clear, legally accurate definition in each language. The three definitions must describe the same legal concept, not merely be word-for-word translations.
- Legal domain (for example: constitutional, civil, civil procedure, criminal, criminal procedure, evidence, family, land, labour, commercial, administrative, or other existing taxonomy).
- Jurisdiction (Federal Ethiopia, Oromia, or other jurisdiction only when supported by the source).
- Context/usage note where a term has a specific Ethiopian legal meaning or differs from ordinary usage.
- Source references supporting the definition and terminology. Where available, record legislation/proclamation/regulation title and number, article, court decision/cassation reference, official legal dictionary, publication, page, and a verifiable URL or document reference.
- Date/version and review status.

C. Add a new term / suggest a correction
- Add an “Add term” action for authenticated users who are permitted by the existing application access policy.
- The submission form should support: source/preferred term, language, proposed equivalent terms in the other two languages (optional at submission), definitions, legal domain, jurisdiction, synonyms, context/usage note, and source references.
- Allow a user to submit a term even when they do not know all three translations. Mark missing translations as incomplete and require a qualified reviewer to complete or verify them before publication.
- Allow users to suggest corrections to an existing entry without directly overwriting the approved entry.
- Validate required fields, maximum lengths, supported languages, URLs, and source-reference structure on the server as well as the client.
- Show the submitter a confirmation and the status of their own submissions. Do not represent a pending suggestion as approved legal terminology.

D. Review and publication workflow
- Reuse the application's existing RBAC roles and permission checks. Inspect actual role names and helper functions before implementation; do not invent new privileged roles or grant additional access by default.
- Users with the existing authorized legal-review/admin permission may review, edit, approve, reject, or request changes to submissions.
- Auditors or read-only roles must not be able to alter glossary entries unless the existing policy explicitly grants that permission.
- An entry may become approved/published only after a reviewer verifies all three language terms, all three definitions, legal domain, jurisdiction, and supporting references (or records a justified reason why a source reference is not applicable).
- Do not auto-publish machine-generated translations. AI may suggest translations for a reviewer, but suggestions must be labelled “AI draft — unverified” and must never be presented as established legal terminology until a human reviewer approves them.
- Preserve the previous approved version when a correction is approved. Record who submitted, who reviewed, what changed, when it changed, the decision, and the reason. Use the existing audit-log mechanism if available; otherwise add a narrowly scoped append-only audit record.
- Rejected and pending submissions must remain distinguishable from approved glossary entries. Provide a reason/status to the submitter where permitted.

LEGAL TERMINOLOGY ACCURACY — NON-NEGOTIABLE
1. Do not invent legal terms, translations, definitions, statute numbers, article numbers, court decisions, citations, or URLs.
2. Preserve established Ethiopian legal terminology. Do not replace a recognized legal term with a casual, approximate, or stylistically attractive expression.
3. Treat Afaan Oromoo, Amharic, and English as legal languages with their own established terminology. A translation is acceptable only if it preserves the legal concept and its scope in the relevant jurisdiction.
4. Do not assume that one English term always has one exact equivalent in Afaan Oromoo or Amharic. Where one-to-one equivalence is not reliable, record a carefully explained translation note, alternative equivalent, or “no exact equivalent” status for reviewer resolution.
5. Distinguish legal meanings from ordinary meanings and distinguish concepts that are similar but not identical (for example, a right, remedy, cause of action, jurisdiction, admissibility, burden of proof, and standard of proof must not be collapsed into one concept).
6. If Federal Ethiopian law and Oromia law use different terminology or definitions, preserve the distinction through jurisdiction and source metadata. Do not merge them into one definition without explanation.
7. Definitions must be neutral, concise, conceptually accurate, and understandable to legal professionals and the public. They must not give case-specific legal advice.
8. Every published definition must be traceable to its listed source(s) or explicitly marked as a reviewed general legal definition. Never fabricate a source to fill a required field.
9. If reliable evidence is insufficient, save the submission as pending/incomplete and request legal review instead of guessing.

DATA MODEL AND STORAGE
First inspect the existing Firestore conventions and security rules. Adapt names/paths to the existing architecture; do not blindly create duplicate systems. Use a structure equivalent to the following if no suitable glossary model already exists:

Approved glossary entry:
{
  termId: string,
  conceptId: string,
  terms: {
    om: { preferred: string, synonyms: string[] },
    am: { preferred: string, synonyms: string[] },
    en: { preferred: string, synonyms: string[] }
  },
  definitions: { om: string, am: string, en: string },
  usageNotes: { om?: string, am?: string, en?: string },
  translationNotes?: { om?: string, am?: string, en?: string },
  domain: string,
  jurisdiction: string[],
  sourceReferences: SourceReference[],
  status: 'approved' | 'archived',
  version: number,
  createdAt: server timestamp,
  updatedAt: server timestamp,
  createdBy: string,
  updatedBy: string,
  reviewedAt: server timestamp,
  reviewedBy: string
}

SourceReference should support structured fields such as sourceType, title, issuingBody, identifier/number, articleOrSection, volume, page, publicationDate, documentId, and url. Only store fields that are actually known and verified.

Submission/revision record:
{
  submissionId: string,
  submissionType: 'new_term' | 'revision',
  targetTermId?: string,
  proposedEntry: object,
  status: 'pending' | 'needs_changes' | 'approved' | 'rejected',
  submittedBy: string,
  submittedAt: server timestamp,
  reviewedBy?: string,
  reviewedAt?: server timestamp,
  reviewerNote?: string
}

Search index:
- Generate normalized search fields/tokens from all three preferred terms, approved synonyms, and definitions.
- Generate tokens in trusted backend code or the existing indexing service; never trust client-supplied search tokens.
- Use the project's existing search service if it already supports multilingual legal search. Otherwise implement a Firestore-compatible indexed search approach with the required indexes and pagination.
- Do not claim Firestore provides native full-text search. Document the search method and its limitations.
- Ensure search results are restricted to approved glossary entries for normal users.
